## 1. Problem Statement

Autonomous coding agents (such as Claude Code, Cursor, and related terminal/IDE agents) execute locally on developer machines with unconstrained user-level permissions. In order to complete tasks, agents autonomously traverse directory trees, grep across repository files, and ingest file contents into their prompt context windows. Whatever is ingested is transmitted across HTTPS to third-party model inference endpoints.

This workflow introduces three critical security vulnerabilities:

1. **Prompt-Level Guidance is Not Access Control**: Directing an agent via system prompts (e.g., *"Do not open `.env`"* or *"Do not read private keys"*) is merely advisory. In practice, exploratory agent tool loops, deep context window drift, or prompt injection embedded in repository files consistently cause agents to inspect forbidden files anyway.
2. **Permanent Credential Exfiltration**: Once an agent reads an uncommitted `.env`, SSH private key, cloud credential, or unpublished paper draft, that text becomes part of the outgoing API payload. A single read constitutes an irreversible data leak.
3. **Absence of Independent Observability**: Standard developer workflows provide no independent, unforgeable mechanism to answer what files an agent actually read, how many bytes were transferred, or whether access restrictions held. Trust is placed entirely on self-reported agent summaries.

Coarse-grained workarounds fail in practice:
- Full containers or virtual machines sever access to the host tools and runtimes required for active development.
- In-agent permission popups create high developer fatigue and still depend on the agent process enforcing rules against itself.
- Simple file overlays (e.g., binding `/dev/null` over `.env`) leave the file visible as an empty file, fail to handle files created dynamically during the session, and provide zero read auditing.

## 2. Objectives and Design Goals

### Functional Objectives
- **G1: Selective Hiding**: Forbidden files and directories matching user-defined deny patterns must be completely invisible. Directory listings must omit them, and lookup attempts must return `ENOENT` ("No such file or directory") rather than `EACCES` ("Permission denied"), denying the agent knowledge that the file exists.
- **G2: Byte-Accurate Read Tracking**: Every file access permitted through the filesystem must record the relative path, exact byte count transferred, caller process ID (PID), process name, and high-resolution timestamp.
- **G3: Tamper-Evident Block Tracking**: Every direct attempt to probe, stat, open, or write to a forbidden path must be intercepted and logged with the decision marked as `blocked` (or `would_block` in audit mode).
- **G4: Prompt-Blind & Content-Blind Operation**: AI Guard operates strictly at the operating system filesystem call layer. It never inspects, parses, or stores prompts, code content, or file payloads. Access logs contain metadata only.
- **G5: Low Developer Friction**: Declarative rule definition through a single YAML configuration file, requiring zero interactive prompts during active coding sessions.
- **G6: Agent-Agnostic Execution**: Capable of sandboxing any unprivileged binary, including Node.js agents, Python CLIs, and standalone binaries.
- **G7: Dual Research Modes**: Full support for both `enforce` mode (active blocking and hiding) and `audit` mode (transparent pass-through logging) to provide empirical baselines for research evaluation.

### Non-Functional Requirements
- **NFR1: Strict Zero-Content Logging**: File payloads and prompt strings are strictly excluded from logging structures.
- **NFR2: Log Permissions**: Telemetry files are enforced with Unix permissions `0600` (readable and writable only by the owner).
- **NFR3: Measurable Overhead**: Interception overhead is benchmarked to ensure agent interactivity is maintained.
- **NFR4: Fail-Closed Security**: If the GuardFS daemon terminates or is killed, the sandbox loses access to `/workspace` entirely rather than falling back to the raw, unprotected host filesystem.

## 3. Research Novelty & Threat Model

### Threat Model
- **Target Threat**: A coding agent running as a standard, unprivileged user process. The agent is assumed to be capable of unintended file discovery, aggressive tree traversal, or being manipulated by indirect prompt injections placed within third-party repository code.
- **Protected Assets**: Any file or directory matching deny patterns (e.g., credentials, private keys, documents), user home directories outside the project (`~/.ssh`, `~/.aws`), and parent process environment variables.
- **Trusted Computing Base**: The Linux kernel, FUSE subsystem (`/dev/fuse`), Bubblewrap (`bwrap`), and the user configuration.
- **Explicit Non-Goals**: Root-level privilege escalation exploits, malicious kernel modules, timing side-channels, or secrets manually pasted into the agent terminal by the user.

### Comparison With Existing Approaches

| Security Approach | Enforcement Mechanism | Selective File Hiding? | Independent Read Audit? | Primary Failure Mode |
|---|---|---|---|---|
| Prompt Instructions | Model Alignment | No | No | Ignored during exploration or injection |
| Per-Read Prompts | Agent Application UI | No | Partial | High friction; trusts the agent process |
| In-Agent Deny Lists | Agent Process Logic | No | Partial | Bypassed if agent process is compromised |
| Full Docker / VM | OS Virtualization | Coarse only | No | Breaks local development tools & setup |
| **AI Guard** | **External OS FUSE + bwrap** | **Yes (Full ENOENT)** | **Yes (Byte-level JSONL)** | **Fails closed if daemon stops** |

## 4. Architecture & Technical Implementation

AI Guard places an external filtering layer between the coding agent and the physical storage device:

```
Physical Project Directory (~/projects/myapp)
               │
               ▼
┌──────────────────────────────────────────────┐
│  GuardFS (Custom Python FUSE Operations)     │
│   - Selective path matching (fnmatch)        │
│   - Invisibility in readdir (entries hidden) │
│   - Forbidden open / stat -> ENOENT          │
│   - Symlink & hardlink traversal mitigation  │
│   - Direct I/O byte-level access logging     │
└──────────────────────────────────────────────┘
               │
               ▼ Mounted at ~/.aiguard/mnt/myapp
┌──────────────────────────────────────────────┐
│  Bubblewrap (bwrap) Isolation Sandbox        │
│   - Mount namespace: /workspace = GuardFS    │
│   - PID namespace isolation (--unshare-pid)  │
│   - Cleared environment (--clearenv)         │
│   - Isolated temporary home (/home/sandbox)  │
│   - Host ~/.ssh and credentials inaccessible │
└──────────────────────────────────────────────┘
               │
               ▼
         Coding Agent (e.g., Claude Code, Cursor, terminal runner)
               │
               ▼ Output
         Model API Endpoint (Forbidden file contents never reach it)
```

### Core Components
1. **`aiguard/rules.py`**: A pattern matching engine supporting root-relative paths, multi-depth wildcard extensions (`*.pem`, `*.pdf`), and full directory subtree blocking (`secrets/`).
2. **`aiguard/logger.py`**: A thread-safe, non-blocking JSONL telemetry recorder enforcing mode `0600` and sanitizing dictionary fields against sensitive data keys.
3. **`aiguard/guardfs.py`**: A FUSE filesystem subclassing `fusepy.Operations`. Enforces direct I/O (`direct_io=True`) and zero attribute caching (`attr_timeout=0`) so every filesystem request traverses the guard without being hidden by kernel page cache hits.
4. **`aiguard/sandbox.py`**: Programmatically builds and launches `bwrap` sandboxes, configuring sanitized environment variables (`PATH`, `TERM`, `LANG`) and binding essential system directories (`/usr`, `/etc`, `/dev`, `/proc`).
5. **`aiguard/cli.py`**: Unified command-line interface supporting agent execution, health diagnosis, direct mounting for IDEs, and compliance auditing.
6. **`aiguard/auditor.py`**: An automated compliance verification agent that programmatically audits the running code against Problem Statement, Objectives, and Research Novelty requirements.

## 7. How to Use AI Guard in ANY Project (Zero Friction & Transparent)

Once installed, you never need to copy AI Guard code into your projects. You can protect any repository on your computer with simple commands.

### Step 1: Initialize Protection in Your Project (`aiguard init`)
Navigate to your project folder (e.g. `mercy_project`):
```bash
cd ~/projects/mercy_project
aiguard init
```

**What happens immediately:**
- **Automated Secret Discovery**: AI Guard scans the project for sensitive files and folders (`.env`, `secrets/`, private keys, certificates, confidential documents).
- **Generates `.aiguardignore`**: Declarative rules list. Remove any line if you want AI agents to read that item; add lines to hide additional files or folders.
- **Generates `aiguard-log.sh`**: Live executable monitor script. Run it in a side terminal to watch file reads and blocked attempts in real-time.
- **Git Security**: Automatically updates (or creates) `.gitignore` to ensure `.aiguard/`, `.aiguardignore`, `aiguard-log.sh`, and `*.jsonl`/`access.json` are **never committed or pushed to GitHub**.
- **Configures Transparent Agent Alias**: Automatically registers `alias claude='aiguard run -- claude'` in your shell config (`~/.bashrc`), enabling you to launch agents normally without typing wrapper commands.
- **Zero Project Clutter**: No heavy python packages, virtualenvs, or clutter are copied into your repository.

*(To restore your project to clean state at any time, run: `aiguard deinit`)*

---

### Step 2: Run Your AI Coding Agent

#### 1. Claude Code CLI (Default & Transparent)
Because `aiguard init` configures shell aliases automatically, you can simply type your normal agent command:
```bash
claude
```
*(Tip: In your current terminal session, run `source ~/.bashrc` or open a new terminal window for the alias to become active immediately).*  
Under the hood, this transparently routes Claude through the AI Guard Bubblewrap sandbox and GuardFS FUSE filesystem!

#### 2. Google Antigravity (AGY)
- **Terminal CLI (`agy`)**:
  ```bash
  aiguard run -- agy
  # Or add alias: alias agy='aiguard run -- agy'
  ```
- **Antigravity IDE**:
  Mount the protected project, then open the mountpoint in Google Antigravity:
  ```bash
  aiguard mount
  agy ~/.aiguard/mnt/<project_name>
  ```

#### 3. OpenAI Codex, Cursor & Other Terminal Agents
- **Direct Terminal Execution**:
  ```bash
  aiguard run -- codex
  aiguard run -- cursor-agent
  ```
- **Shell Alias for Any Agent**:
  Add an alias to your `~/.bashrc` for any agent binary:
  ```bash
  alias codex='aiguard run -- codex'
  alias cursor-agent='aiguard run -- cursor-agent'
  ```

#### 4. Interactive Sandboxed Shell
To inspect the sandboxed filesystem view or run multiple tools:
```bash
aiguard run bash
```

> [!NOTE]
> ### Architecture Note: Why does `aiguard run` exist if `aiguard init` is already run?
> **Operating System Process Isolation**:  
> In Linux, every terminal process runs in its own memory and process space. When you run `aiguard init`, it defines the **protection policy** (`.aiguardignore`), Git exclusion rules, and logs. However, the Linux kernel does not allow external user-space tools to involuntarily hijack arbitrary terminal commands unless the process is launched inside a mount namespace.
> 
> If someone types raw `claude` without a sandbox or alias, the OS kernel gives it direct, unmediated access to physical disk inodes.
> 
> Therefore, AI Guard provides:
> 1. **`aiguard run`**: Creates an unprivileged Bubblewrap mount namespace where `/workspace` is dynamically attached to the custom GuardFS FUSE driver.
> 2. **Automatic Shell Aliases (`alias claude='aiguard run -- claude'`)**: Bridges this seamlessly so developers get 100% of the security without changing their daily typing habits.
> 3. **Auto-Init Fallback**: If you run `aiguard run claude` in an uninitialized directory, AI Guard auto-initializes safe defaults on the fly so secrets are never left unprotected.

### Step 3: Watch Live Access and Audit Logs

#### Real-Time Telemetry Monitor (`./aiguard-log.sh`)
Open a second terminal window in your project and run:
```bash
./aiguard-log.sh
```
*(Or run `aiguard logs -f` from anywhere)*  
You will see a real-time live stream of every file read, exact byte count, process name, and blocked attempt as the AI agent works!

#### Post-Session Access Audit & JSON Export
When the agent finishes its session, all access history is preserved in `~/.aiguard/logs/access.jsonl`. You can inspect the audit summary or export it to JSON:
```bash
# View terminal summary with byte counts & blocked paths:
aiguard logs

# Export complete session telemetry to a formatted JSON file:
aiguard logs --export access.json

# Dump raw JSON array to stdout:
aiguard logs --json
```

- **Data Serialization**: PyYAML, JSON / JSONL
- **Analytical & Reporting Framework**: Pandas, NumPy, Matplotlib, Jupyter Notebook
- **Testing & Verification Framework**: Pytest, Bash, POSIX Utilities
